# TTL 产品方向与使用形态

状态：提案，待后续评审和删减

本文记录 TTL 面向公开使用的产品定位、主要交互形态和阶段性范围。它描述目标方向，不代表所有候选功能都已经承诺实现。

## 1. 产品定位

TTL 定位为一个本地优先、面向开发者的知识资源管理工具：

> 以 TUI 为主要使用入口，以 CLI 作为脚本和自动化接口。

主要用于保存和查找命令、配置片段、链接、文件路径以及其他值得长期保留的文本。

TTL 不以替代 Notion、Obsidian 或企业知识库为目标，重点是降低个人资源的记录、查找和修改成本。

## 2. 已确认的方向

- 目标用户不局限于作者本人，其他开发者也应能安装和使用。
- TUI 是主要交互形态，CLI 继续保留为快速操作和自动化入口。
- 数据模型暂时保持简单的 key、value、tags 和时间字段。
- 工作日志保留，但定位为低优先级的审计和辅助功能。
- 同步冲突的自动合并和 CRDT 暂不实现，后续再评估。
- 外部集成暂不纳入当前阶段，包括浏览器、Raycast 和剪贴板集成。
- AI、自然语言操作和 MCP 暂不纳入当前方向。
- 原生桌面端、移动端、多人协作和 SaaS 暂不纳入当前方向。

## 3. 使用形态

### 3.1 CLI

CLI 保留作为稳定底座，适合快速记录、脚本、SSH 和自动化任务。

保留现有快捷命令以兼容已有使用方式：

```bash
ttl add
ttl get
ttl update
ttl del
ttl tag
```

逐步补充更清晰的命令：

```bash
ttl list
ttl search
ttl edit
ttl copy
ttl ui
```

CLI 和 TUI 应共享同一套业务逻辑，避免 TUI 直接依赖 CLI 命令的全局状态或文本输出。

### 3.2 TUI

建议入口为：

```bash
ttl ui
```

主界面包含当前工作区、搜索框、资源列表和内容预览区域。主要操作包括：

- `/` 搜索 key、value 和 tag
- 上下键切换资源
- Enter 查看详情
- `e` 编辑
- `t` 管理标签
- `c` 复制内容
- `o` 打开链接或文件
- `d` 删除并确认
- `w` 切换工作区
- `s` 查看同步差异
- `q` 退出

TUI 必须覆盖空数据库、搜索无结果、内容过长、编辑未保存、删除确认、数据库错误和工作区切换等状态。

### 3.3 本地 Web UI

本地 Web UI 作为后续可选形态，不作为第一阶段目标。若实现，默认只监听 `127.0.0.1`，并复用已有存储和业务服务。

当前 API 主要覆盖资源、审计和历史。支持 Web UI 前，需要补充日志、标签、工作区、导入导出、同步预览和批量操作等接口。

## 4. 第一阶段目标

第一阶段只验证本地资源管理的完整闭环：

```text
安装
→ 启动 TUI
→ 添加资源
→ 搜索内容
→ 查看详情
→ 编辑、复制、打标签
→ 安全删除
```

如果这条流程足够顺畅，项目才具备让其他人安装和长期使用的基础。

### 4.1 CLI 基础能力

- [ ] 搜索 key、value 和 tag
- [ ] 增加明确的 `list` 和 `search` 命令
- [ ] 列表显示摘要、标签和更新时间
- [ ] 支持 `--json`，方便脚本和 TUI 调用
- [ ] 支持从 stdin 读取多行内容
- [ ] 支持使用 `$EDITOR` 编辑资源
- [ ] 支持复制资源内容
- [ ] 删除操作增加确认机制
- [ ] `update` 成功后输出明确提示
- [ ] 完善稳定退出码和错误提示

目标示例：

```bash
ttl add nginx -
ttl search "8080"
ttl edit nginx
ttl copy nginx
ttl list --tag docker
```

### 4.2 对外发布能力

- [ ] 提供 Linux、macOS 和 Windows 发布包
- [ ] 支持稳定的安装方式，例如 `go install` 或发布脚本
- [ ] 首次启动自动初始化
- [ ] README 示例与实际命令保持一致
- [ ] `ttl --help` 和子命令帮助可直接使用
- [ ] 明确数据库格式和升级迁移策略
- [ ] 提供备份和恢复能力
- [ ] 保证本地数据文件权限合理

## 5. 资源模型

第一阶段保持以下核心字段：

```text
key
value
tags
created_at
updated_at
```

可以预留但不强制使用：

```text
kind       text / url / command / code
favorite   bool
archived   bool
```

附件、关联资源、自动摘要、知识图谱和复杂富文本编辑器暂不纳入第一阶段。

## 6. 搜索设计

搜索是核心能力，至少覆盖：

- key
- value
- tag

后续可增加模糊匹配、多关键词、标签过滤、最近修改排序、最近使用排序、收藏优先和搜索摘要。

## 7. 同步策略

同步暂时属于高级功能，不应影响默认的本地单机体验。

当前仅保留明确的单向操作和预览能力：

```bash
ttl sync --dry-run
ttl sync --direction pull
ttl sync --direction push
```

在自动冲突合并和 CRDT 实现前，应满足以下约束：

- 默认先展示变更计划，不直接删除数据。
- pull 和 push 都需要明确确认。
- 冲突采用简单、可解释的策略。
- 不将当前同步描述为智能合并。
- 数据结构为未来的版本字段和变更日志预留空间。

## 8. 工作日志

工作日志保留为次级模块，用于审计和辅助记录，不进入 TUI 主界面。

第一阶段只需要支持：

- 记录
- 按日期查看
- 删除
- 导出

AI 周报、复杂统计和自动总结暂不实现。

## 9. 推荐开发顺序

```text
阶段 1：统一 CLI、修正文档、稳定数据格式
阶段 2：增加全文搜索、编辑器、复制、备份
阶段 3：实现 TUI 主流程
阶段 4：补齐跨平台发布和首次使用体验
阶段 5：完善工作区和同步
阶段 6：根据真实用户反馈评估 Web UI 和其他集成
```

## 10. 验收标准

第一版 TUI 至少应满足：

- 新用户无需阅读大量文档即可启动。
- 用户能在较短时间内完成第一条资源的添加和搜索。
- 即使不记得 key，只记得内容，也能找到资源。
- 全程可以只用键盘完成主要操作。
- 编辑、复制和打标签不需要退出 TUI。
- 删除和同步不会默认造成数据丢失。
- CLI 和 TUI 操作的是同一份数据。
- Linux、macOS 和 Windows 能完成基础操作。

## 11. 当前不做

为避免项目过早扩张，当前明确不做：

- 原生桌面客户端
- 原生移动端
- 多人协作和权限系统
- 在线 SaaS 服务
- AI 自然语言操作
- MCP 集成
- 复杂知识图谱
- 大量第三方入口集成

当前路线可以概括为：

```text
本地优先
TUI 优先
CLI 保留
搜索优先
稳定性优先
同步后置
AI 暂停
```
