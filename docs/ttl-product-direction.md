# TTL 工程能力边界与范围基线

状态：已确认（基础 TUI / W-007 范围）
版本：v0.2
日期：2026-09-12

评审：[TUI、CLI 与客户端边界设计评审与整改复核](reviews/2026-09-12-tui-client-boundary-design.md)（`PASS`；仅基础 TUI / W-007 范围）

本文是 TTL 的产品范围和工程能力边界基线，用于判断一个需求是否属于当前工程、当前阶段或明确不属于本项目。后续需求、技术方案、任务拆分和实现都必须引用本文；本文未确认的能力不得因为出现在路线图、讨论记录或代码草稿中而视为承诺。

本文负责产品定位、范围、工程边界和非目标。TUI 交互细节由 [`tui-master-plan.md`](tui-master-plan.md) 负责，但不得突破本文基线；当前存储、后端和同步行为以 [`client-server-data-flow.md`](client-server-data-flow.md) 与代码为准。

## 1. 文档定位与生效规则

### 1.1 基线的作用

- 限定 TTL 当前要解决的问题、服务对象和主要使用形态。
- 区分当前已有能力、当前阶段承诺、长期候选和明确不做。
- 为需求评审提供唯一的范围入口，防止把技术可能性直接变成产品需求。
- 为客户端、服务端、存储、同步和开发阶段契约变更提供不可隐式突破的工程边界。

### 1.2 生效条件

本文已完成关联评审中的范围收敛并由项目负责人确认。已确认的阶段承诺对基础 TUI / W-007 生效；候选能力仍须完成独立的范围变更、需求、技术方案和评审后才能进入实现。

### 1.3 适用对象

本文约束产品需求、CLI/TUI 设计、服务端和同步能力、数据模型扩展、发布能力以及相关任务拆分。它不替代当前实现说明、技术方案、测试规范或任务状态板。

当前基线的需求展开见 [`docs/requirements/2026-09-12-capability-boundary-baseline.md`](requirements/2026-09-12-capability-boundary-baseline.md)。

## 2. 产品定位

TTL 定位为一个本地优先、面向开发者的知识资源管理工具：

> 以 TUI 为主要使用入口，以 CLI 作为脚本和自动化接口。

主要用于保存和查找命令、配置片段、链接、文件路径以及其他值得长期保留的文本。

TTL 不以替代 Notion、Obsidian 或企业知识库为目标，重点是降低个人资源的记录、查找和修改成本。

## 3. 工程边界

### 3.1 应用边界

- `ttl` 是运行在用户设备上的客户端应用，CLI 和 TUI 是同一客户端的两种交互形式。
- `ttl-server` 是独立的云端服务应用，拥有独立的构建、配置、发布和运行环境。
- CLI、TUI 和服务端不各自实现一套业务规则；它们应共享明确的领域和存储契约。
- CI 只是 CLI 的无 TTY 运行环境，不是第三种客户端。

### 3.2 产品和数据边界

- 产品默认本地优先；网络、API Key 或同步服务不可用时，本地资源的查看和编辑不应被阻塞。
- 资源默认归单一账户或单一工作区所有，不提供跨账户分享、协作者、资源级权限或多人实时编辑。
- 项目处于开发阶段，CLI 语义、数据文件、配置格式、存储契约和 `/api/v1` 接口均可直接调整；改变它们时同步更新全部调用方、数据、测试和文档。
- 破坏性操作必须可解释、可确认，不能把同步或批量操作默认为无提示覆盖或删除。

## 4. 能力状态分类

能力状态和实现进度必须分开记录。能力状态决定能否进入需求；实现进度只说明代码完成情况。

| 状态 | 含义 | 是否可以直接进入新需求 |
| --- | --- | --- |
| `现有能力` | 当前代码已经提供，行为以代码和当前实现文档为准 | 只有在需求明确引用现有行为时可以 |
| `阶段承诺` | 已被本基线确认，当前阶段必须交付 | 可以，必须写可验收标准 |
| `候选能力` | 有价值但尚未承诺，等待单独评审 | 不可以，必须先完成范围变更 |
| `明确不做` | 当前工程或当前阶段明确排除 | 不可以，除非重新评审并更新基线 |

下面的 `P0-P3` 只表示优先级，不代表自动承诺。没有 `阶段承诺` 状态的能力，不得仅凭优先级进入实现任务。

## 5. 基线承诺与候选范围

### 5.1 当前阶段承诺

在基线确认后，当前阶段只承诺验证本地资源管理闭环：

```text
安装
→ 启动 ttl 客户端
→ 添加资源
→ 按 key、value 或 tag 搜索
→ 查看详情
→ 编辑和维护标签
→ 安全删除
```

首期复用现有的 `key`、`value`、`tags`、`created_at` 和 `updated_at` 字段，不因 TUI 或单项需求自动新增 `kind`、`favorite`、`archived`、附件、关联资源或复杂富文本字段。

CLI 必须继续保留并维持既有核心命令语义；CLI 和 TUI 操作同一份本地数据，并共享业务规则。首期是否同时交付新的 JSON、非交互、`ttl pick`、剪贴板或外部编辑器契约，必须在对应需求中单独确认，不从 TUI 需求自动推导。

W-012 已单独确认进入阶段承诺：为 `add/get/update/del/tag/dtag` 建立 JSON、非交互、stdin/stdout/stderr 和稳定机器退出码契约。它独立于基础 TUI 交付，不扩展为 `search`、`pick` 或其他命令。

### 5.2 候选能力

候选能力不属于当前阶段承诺，具体清单统一维护在 [`TTL 后续能力规划`](ttl-future-roadmap.md)。候选能力只有在单独的需求、技术设计、方案评审和任务项完成后，才能转为阶段承诺。

## 6. 方向原则（不等于首期交付）

- 目标用户不局限于作者本人，其他开发者也应能安装和使用。
- 产品包含本地 `ttl` 客户端和云端 `ttl-server` 服务两个独立应用工程；两者可以共用源码仓库，但必须分别构建、发布和运行。
- TUI 是主要交互形态，CLI 继续保留为快速操作和自动化入口。
- 数据模型暂时保持简单的 key、value、tags 和时间字段。
- 工作日志保留，但定位为低优先级的审计和辅助功能。
- 同步冲突的自动合并和 CRDT 暂不实现，后续再评估。
- 外部集成暂不纳入当前阶段，包括浏览器、Raycast 和剪贴板集成。
- AI、自然语言操作和 MCP 暂不纳入当前方向。
- 原生桌面端、移动端、多人协作和 SaaS 暂不纳入当前方向。

## 7. 使用形态

### 7.1 CLI

CLI 保留作为稳定底座，适合快速记录、脚本、SSH 和自动化任务。

当前核心快捷命令包括：

```bash
ttl add
ttl get
ttl update
ttl del
ttl tag
```

以下命令属于后续候选增强，不构成当前阶段承诺：

```bash
ttl list
ttl search
ttl edit
ttl copy
ttl ui
```

CLI 和 TUI 应共享同一套业务逻辑，避免 TUI 直接依赖 CLI 命令的全局状态或文本输出。

### 7.2 TUI

建议入口为：

```bash
ttl ui
```

目标形态包含当前工作区、搜索框、资源列表和内容预览区域。首期只承诺资源列表、按 key/value/tag 搜索、详情、编辑、标签维护和安全删除；以下操作属于后续候选扩展：

- `/` 搜索 key、value 和 tag
- 上下键切换资源
- Enter 查看详情
- `e` 编辑
- `t` 管理标签
- `d` 删除并确认（首期）
- `c` 复制内容（候选）
- `o` 打开链接或文件（候选）
- `w` 切换工作区（候选）
- `s` 查看同步差异（候选）
- `q` 退出

首期 TUI 必须覆盖空数据库、搜索无结果、内容过长、编辑未保存、删除确认和数据库错误等本地闭环状态；工作区切换属于候选扩展。

### 7.3 本地 Web UI

本地 Web UI 作为后续可选形态，不作为第一阶段目标。若实现，默认只监听 `127.0.0.1`，并复用已有存储和业务服务。

当前 API 主要覆盖资源、审计和历史。支持 Web UI 前，需要补充日志、标签、工作区、导入导出、同步预览和批量操作等接口。

## 8. 第一阶段目标

第一阶段只验证本地资源管理的完整闭环。下面的细化清单是后续需求展开的输入；清单中的待实现项不自动扩大本节的承诺范围。

```text
安装
→ 启动 TUI
→ 添加资源
→ 搜索内容
→ 查看详情
→ 编辑、打标签
→ 安全删除
```

如果这条流程足够顺畅，项目才具备让其他人安装和长期使用的基础。

### 8.1 CLI 能力池

现阶段核心命令为 `add/get/update/del/tag`；这些命令允许随已确认需求直接调整。以下清单中的新增命令和契约均需单独确认，不因列在本节而成为首期交付：

- [ ] 搜索 key、value 和 tag
- [ ] 增加明确的 `list` 和 `search` 命令
- [ ] 列表显示摘要、标签和更新时间
- [ ] 支持 `--json`，方便脚本和 TUI 调用
- [ ] 支持从 stdin 读取多行内容
- [ ] 支持使用 `$EDITOR` 编辑资源
- [ ] 支持复制资源内容
- [ ] 删除操作增加确认机制
- [ ] `update` 成功后输出明确提示
- [ ] 完善稳定退出码和错误提示

目标示例：

```bash
ttl add nginx -
ttl search "8080"
ttl edit nginx
ttl copy nginx
ttl list --tag docker
```

### 8.2 对外发布能力（候选）

- [ ] 提供 Linux、macOS 和 Windows 发布包
- [ ] 支持稳定的安装方式，例如 `go install` 或发布脚本
- [ ] 首次启动自动初始化
- [ ] README 示例与实际命令保持一致
- [ ] `ttl --help` 和子命令帮助可直接使用
- [ ] 明确数据库格式和升级迁移策略
- [ ] 提供备份和恢复能力
- [ ] 保证本地数据文件权限合理

## 9. 资源模型

第一阶段保持以下核心字段：

```text
key
value
tags
created_at
updated_at
```

可以预留但不强制使用：

```text
kind       text / url / command / code
favorite   bool
archived   bool
```

附件、关联资源、自动摘要、知识图谱和复杂富文本编辑器暂不纳入第一阶段。

## 10. 搜索设计

搜索是核心能力，至少覆盖：

- key
- value
- tag

后续可增加模糊匹配、多关键词、标签过滤、最近修改排序、最近使用排序、收藏优先和搜索摘要。

## 11. 同步策略

同步暂时属于高级功能，不应影响默认的本地单机体验。

当前仅保留明确的单向操作和预览能力：

```bash
ttl sync --dry-run
ttl sync --direction pull
ttl sync --direction push
```

在自动冲突合并和 CRDT 实现前，应满足以下约束：

- 默认先展示变更计划，不直接删除数据。
- pull 和 push 都需要明确确认。
- 冲突采用简单、可解释的策略。
- 不将当前同步描述为智能合并。
- 数据结构为未来的版本字段和变更日志预留空间。

## 12. 工作日志

工作日志保留为次级模块，用于审计和辅助记录，不进入 TUI 主界面。

以下是工作日志的现有能力和长期能力清单，不属于首期本地资源闭环的自动承诺：

- 记录
- 按日期查看
- 删除
- 导出

AI 周报、复杂统计和自动总结暂不实现。

## 13. 推荐开发顺序（路线建议，不是交付承诺）

```text
阶段 1：统一 CLI、修正文档、稳定数据格式
阶段 2：增加全文搜索、编辑器、复制、备份
阶段 3：实现 TUI 主流程
阶段 4：补齐跨平台发布和首次使用体验
阶段 5：完善工作区和同步
阶段 6：根据真实用户反馈评估 Web UI 和其他集成
```

## 14. 验收标准

第一版 TUI（基线阶段承诺）至少应满足：

- 新用户无需阅读大量文档即可启动。
- 用户能在较短时间内完成第一条资源的添加和搜索。
- 即使不记得 key，只记得内容，也能找到资源。
- 全程可以只用键盘完成主要操作。
- 编辑和打标签不需要退出 TUI。
- 删除不会默认造成数据丢失。
- CLI 和 TUI 操作的是同一份数据。

跨平台发布、同步和远端一致性属于后续独立需求的验收范围，不作为首期 TUI 的隐含承诺。

## 15. 当前不做

为避免项目过早扩张，当前明确不做：

- 原生桌面客户端
- 原生移动端
- 多人协作和权限系统
- 在线 SaaS 服务
- AI 自然语言操作
- MCP 集成
- 复杂知识图谱
- 大量第三方入口集成

当前路线可以概括为：

```text
本地优先
TUI 优先
CLI 保留
搜索优先
稳定性优先
同步后置
AI 暂停
```

## 16. 范围变更门禁

任何新增需求都必须完成以下检查：

1. 指明对应的基线章节，并标注属于 `现有能力`、`阶段承诺`、`候选能力` 还是 `明确不做`。
2. 在需求文档中同时写清 `In Scope` 和 `Out Of Scope`，不能只写功能愿望。
3. 发现需求属于候选或明确不做时，先停止进入技术设计和编码，补充范围变更说明、影响评估和新的工作项。
4. 任何新增数据字段、公共接口、客户端入口、同步语义或第三方依赖，都必须说明对本基线、全部调用方、现有数据和发布边界的影响。
5. 实现过程中出现的“顺手支持”“顺便重构”不得进入当前任务；应回到需求文档或新建独立任务。
6. 范围变更经评审确认后，先更新本基线，再更新需求、路线图和 `WORK_ITEMS.md`，最后才能开始实现。

## 17. 文档优先级与维护

发生冲突时按以下顺序处理：

1. 当前行为：以代码、测试和 [`client-server-data-flow.md`](client-server-data-flow.md) 为准。
2. 产品范围：以本基线中已确认的 `阶段承诺` 和 `明确不做` 为准。
3. 具体需求：只能在本基线允许的范围内补充使用场景和验收条件。
4. 技术方案和 TUI 路线：不得把候选能力写成已承诺能力。
5. `docs/decisions/`：记录范围变化、契约变更策略和重要取舍的原因，不替代本基线。

本文件每次范围变化都应更新版本、日期和变更记录。评审未通过的内容必须保留为开放问题或候选项，不能通过改写措辞隐式生效。
