# 采用分类型 CRDT 作为版本化同步的暂定方向

日期：2026-09-13
状态：proposed
任务：W-020

## 背景

W-019 将当前数据源固定为 `local` 或 `cloud` 二选一。W-020 在该存储基础上增加独立的
本地与远程同步能力。现有同步主要基于全量快照比较和更新时间，无法可靠表达离线操作、
重复重试、并发修改和删除与修改同时发生的情况。

当前资源的 `value` 是任意文本，`tags` 是集合，不能把所有字段都使用同一种自动合并
规则，也不能因为追求最终一致而静默丢弃一方数据。

## 决定

W-020 暂定采用分类型 CRDT 作为同步基础，具体接口、表结构、版本编码和依赖库在技术
方案阶段确定：

- 不同 key 自动合并，双方副本最终收敛。
- `tags` 使用 OR-Set，新增和删除按操作合并。
- `value` 使用 Multi-Value Register，并发修改保留多个候选值，不执行字符串拼接。
- 删除使用带因果上下文的 tombstone，避免旧副本重新创建资源。
- 删除与并发修改保留双方证据，进入待处理冲突，不自动复活或静默丢弃。
- 审计和历史使用追加式操作记录，重复操作按 `operation_id` 幂等。
- 用户选择本地、远程或输入新值解决冲突时，产生新的版本操作。
- 版本证据至少包含 `operation_id`、`device_id`、`base_version`、版本向量和服务端全局
  同步游标；全局游标只用于增量拉取，不能单独判断冲突。

首期不引入任意文本的字符级或行级 CRDT，不使用 LWW 静默覆盖 `value`。CRDT 负责状态
和操作的可合并性，无法自动判断业务语义时仍由用户确认。

## 备选方案

- LWW Register：实现简单，但会静默覆盖并发修改，无法满足不丢数据要求。
- 全量快照 `push/pull`：适合一次性迁移，不适合离线重试、增量同步和多设备并发。
- 任意文本的字符级 CRDT：可以自动合并文本，但当前 value 的业务语义不保证适合字符
  级拼接，复杂度和误合并风险过高。
- 所有冲突都人工处理：数据安全直观，但 tags 和不同 key 的无冲突变更无法自动收敛，
  操作成本过高。

## 影响

收益：保留并发 value 候选，避免静默数据丢失；tags 和不同 key 可以自动收敛；删除有
明确的因果证据；同步可以按版本增量拉取并安全重试。

代价：本地 SQLite、远端 API、同步游标和冲突 UI 都需要保存因果元数据；当前基于快照
的同步实现不能直接复用；需要定义 tombstone 清理、版本压缩和冲突解决后的历史保留策略。

风险：Multi-Value Register 只能告诉用户存在多个并发候选，不能自动判断哪个 value
符合业务语义；OR-Set 的删除语义和并发删除需要在技术方案中明确；早期客户端与新协议
之间需要迁移和兼容策略。

## 验证

需求阶段验证需求文档和 W-020 任务卡记录了上述暂定规则。技术方案阶段需要补充版本
向量、操作幂等、OR-Set、Multi-Value Register、tombstone、冲突查询/解决和迁移测试；
方案评审通过前不得实现具体 CRDT 协议或依赖库。
