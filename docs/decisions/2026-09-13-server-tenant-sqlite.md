# 服务端按租户使用独立 SQLite 文件

日期：2026-09-13
状态：adopted（历史）；本仓实现归属已由 W-021 替代
任务：W-019

## 背景

> 2026-09-18 更新：后端存储实现已移出本仓库；独立后端的数据布局由其自身决策负责。当前仓库边界见 [`W-021`](2026-09-18-externalize-backend-service.md)。

当前服务端 `StorageManager` 为每个用户打开一个 bbolt 文件，客户端同时存在 SQLite、
bbolt、cloud 和 sync 多种入口。W-019 需要把普通存储收敛为 local/cloud，并让服务端与
客户端的本地存储使用同一类 SQLite 数据库，同时保持租户之间的数据隔离。账号、API Key
和启停状态仍由 `users.json` 管理，不与资源数据库混放。

## 决定

服务端将为每个租户维护独立 SQLite 文件，目标布局为：

```text
/var/lib/ttl-server/
├── users.json
└── tenants/<user-id>/data.sqlite
```

`StorageManager` 按用户 ID 惰性打开并复用 SQLite 句柄，进程退出或租户删除前显式关闭。
SQLite 启用 WAL、busy timeout、受控连接数和 schema migration 版本记录。新版本不兼容旧
bbolt 或旧 SQLite，不提供迁移命令、自动转换或兼容窗口；发现旧文件时直接报错且不修改。
该决定只覆盖存储格式和生命周期，不包含本地与云端同步、版本或 CRDT。

## 备选方案

- **共享 SQLite 文件**：每条查询都必须携带 `tenant_id`，遗漏会造成跨租户越权；在当前
  代码结构下隔离风险更高，因此不采用。
- **继续使用 bbolt 并提供迁移**：会引入兼容窗口、迁移失败和数据转换风险；在当前版本
  直接拒绝旧格式，要求新建数据库。
- **PostgreSQL**：对当前单机、少量并发部署引入额外服务、备份和迁移成本；暂不采用，
  规模变化时另立决策。

## 影响

收益：保留现有按租户隔离边界，统一 SQLite 工具链，便于单租户备份和恢复。代价：
需要实现新格式的 schema 前向升级、文件级并发控制和旧格式检测；租户数量增长时文件管理
和备份编排需要额外运维。风险：不兼容策略会要求用户重新初始化数据，因此错误信息必须
明确指出旧文件未被修改。

## 验证

实现后已通过服务端租户集成测试验证两个租户互不可见、重启后数据可读、句柄可关闭；旧
格式拒绝测试验证文件未被修改；新格式 schema 初始化、租户隔离和重启恢复测试通过。部署
检查验证目录权限和 `users.json` 的 `0600` 权限，因此本记录更新为 `adopted`。
