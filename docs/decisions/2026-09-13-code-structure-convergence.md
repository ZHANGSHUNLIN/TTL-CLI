# 代码结构收敛采用单一归属与一次性切换

日期：2026-09-13
状态：adopted
任务：W-017

## 背景

W-004 已建立客户端、服务端和共享 core 的目标边界，W-006 已消除客户端生产链路对全局 `db.Stor` 的依赖，但仓库仍处于迁移中间态：顶层 `command`、`models`、`db`、`sync`、`conf`、`crypto`、`i18n` 与新的 `internal/*` 包并存，测试仍有旧门面消费者。仅继续在现有结构上添加功能会让新旧依赖继续扩散。

## 决定

W-017 提议采用“单一归属、一次性切换、行为不变”的收敛策略：

- 保留单仓库、单 Go module，以及 `ttl`/`ttl-server` 两个正式可执行入口。
- 以 `internal/client`、`internal/server`、`internal/core`、`internal/storage` 为最终结构主干；命令适配、客户端用例、同步、配置和加密各有明确 owner。
- 以 `internal/core/resource` 和 `internal/core/storage` 作为共享模型/契约的唯一来源，迁移后删除仅用于别名和转发的旧包。
- 将 CLI 命令适配收敛到客户端边界，将同步能力收敛到 `internal/client/sync`；不再维护根目录同步入口和顶层全局命令作为第二套实现。
- `conf` 和本地 `crypto` 收敛为可被客户端与 bbolt 适配器共用的 `internal/config`、`internal/crypto` 基础包，`i18n` 保留为可被两个命令入口使用的内部共享基础，`util` 按消费者拆分而不是继续扩大泛化包。
- 在一次结构切换中完成所有生产消费者、测试和文档迁移，并删除旧入口；不改变命令、API、配置、数据和同步契约。

本记录在负责人评审通过前保持 `proposed`，不授权开始编码；评审如改变 owner 或兼容策略，应先更新本记录和 W-017 方案。

## 备选方案

- **继续保留新旧结构**：短期风险低，但依赖会继续扩散，维护者无法判断修改入口，不采用。
- **无设计、无内部顺序的一次性重写**：行为回归、import cycle 和测试断裂难以定位；本次采用有依赖顺序的统一切换，不采用无序重写。
- **拆成两个仓库或多个 Go module**：超出当前结构收敛目标，并引入版本联动和发布成本，暂不采用。
- **所有包都塞入 `internal/client`**：入口、用例、适配器和共享契约仍会混杂，不采用。

## 影响

收益：代码归属可由目录和依赖方向直接判断；CLI/TUI 可以复用同一 app/core 契约；服务端不会链接客户端实现；旧包可以在有证据的前提下删除。

代价：需要在一次变更窗口内迁移大量 import、测试和全局输出/flag 使用；切换前准备和一次性回归成本较高。

风险：包移动可能产生 import cycle，测试迁移可能暴露旧全局状态依赖，删除旧包可能影响未记录的外部调用方。控制方式是切换前依赖盘点、架构测试、全量回归和整体回滚点。

维护要求：新增代码不得引用已标记淘汰的顶层包；结构变化必须同步更新 `PROJECT_OVERVIEW.md`、拆分方案、架构测试和 W-017 证据。

## 验证

- 方案评审确认 ownership 表、行为不变规则和删除门禁。
- WBS 内部步骤按依赖顺序完成后，统一运行单测、架构检查和集成/CLI 回归。
- 一次切换结束时，`go list` 和源码扫描证明无生产、测试消费者，旧包已删除。
- 最终运行 `go test ./...`、`go test -race ./...`、`go vet ./...`、`./scripts/verify.sh`、CLI 黑盒回归和两个二进制构建。
- 更新项目导览和任务文档，人工核对代码、测试、文档和状态一致。
