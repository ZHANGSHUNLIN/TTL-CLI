# W-010 独立交付基线

日期：2026-09-13
状态：adopted
任务：W-010

## 背景

源码已经有客户端和服务端入口，但 CI 和 release 仍把仓库当作一个根目录客户端构建。
服务端也缺少进程生命周期和部署恢复契约。需要在实现前确定制品边界、TLS 归属和回滚
要求，避免编码过程中不断改变方向。

## 决定

提议的 v1 基线是：从 `./cmd/ttl-server` 构建 Linux `amd64`/`arm64` 的
`ttl-server` tarball，独立于客户端制品发布并提供 SHA-256 校验。参考部署使用非 root
进程管理器、带版本的 release 目录和 `current` 符号链接。服务端使用显式私有监听地址
和明文 HTTP，公网 TLS 由反向代理或负载均衡器终止。数据保存在独立持久化目录，继续
使用 `users.json` 和每用户 bbolt 文件。升级必须校验制品并备份数据；健康检查失败时
恢复旧 release 指针。

本决定已采用。Linux systemd、进程就绪探针、外部 TLS 终止和不增加 bbolt 版本检查是
W-010 v1 的边界；后续改变这些边界必须另立决策或更新本记录。

## 备选方案

- 只发布一个二进制：拒绝，安装、权限、健康和回滚会继续依赖隐含约定。
- 优先发布 OCI 镜像：后置，当前没有镜像、registry 或容器运行时契约。
- 在 Go 进程内增加直连 TLS 和证书管理：后置，会扩大密钥生命周期并重复部署代理职责。
- 升级时自动迁移数据：拒绝，直到形成独立版本化的迁移和恢复方案。

## 影响

该方案保持仓库和 Go module 共享，同时隔离应用制品和运行权限。代价是增加 CI、发布
和生命周期实现，并要求部署环境维护反向代理和数据备份。本基线不提供高可用、容器
编排、证书签发或跨平台服务端二进制。

## 验证

需要通过 workflow 检查、归档清单/校验检查、干净目录服务端冒烟、健康/关闭测试和临时
升级回滚演练。
