# TUI、CLI/CI 与快速选择器的交互策略

- 状态：proposed
- 日期：2026-09-12
- 关联设计：[TUI 总体设计与长期路线图](../tui-master-plan.md)

## 问题与背景

当前 TTL 主要通过命令行完成查看和操作，能力可用但不适合复杂浏览、预览和编辑。引入 TUI 可以缩短多条资源之间的操作路径，但如果只保留全屏 TUI，会损害脚本、SSH 和 CI 场景；如果直接做系统级弹窗，跨平台和生命周期成本又较高。

产品还明确了以下边界：TUI 是主要交互入口，CLI/CI 必须保留；工作日志是低优先级审计模块；暂不引入 AI、CRDT、后台同步、浏览器或原生系统弹窗。

## 决策

采用“三入口、同一核心”的交互策略：

1. `ttl ui` 提供完整 TUI，用于浏览、搜索、预览、编辑、标签、工作区和后续管理能力。
2. `ttl pick` 提供短生命周期快速选择器，P0 只保证搜索、选择和 `--print`，避免取用单条资源时进入复杂页面。
3. 现有 CLI 继续作为脚本、SSH、CI 和运维入口，提供稳定退出码、JSON、stdin/stdout 和非交互约束。
4. 三个入口只共享 application/core/storage 契约，不互相解析文本输出，也不复制业务规则。
5. 系统级弹窗、CRDT、后台同步和 AI 保持候选或明确不纳入，须基于真实使用数据重新评审。

## 备选方案

### 仅保留全屏 TUI

优点是界面集中、实现入口少。缺点是单条资源取用变慢，并且不能替代 CI 的无 TTY 调用，因此不采用。

### 直接实现原生系统弹窗

优点是全局快捷入口体验好。缺点是需要常驻进程、剪贴板、权限和三平台适配，无法先验证核心工作流，因此延后到 P3 候选。

### 迁移到 Node.js + TypeScript

优点是部分 TUI 组件生态较丰富。缺点是引入运行时和发布复杂度，现有 Go 存储、API 和单二进制优势需要重新建设；当前 TUI 需求不足以抵消迁移成本，因此保留 Go。

## 收益与代价

收益：高频用户有完整 TUI 和快速选择两种路径；自动化用户的 CLI/CI 契约不受影响；业务规则集中后，三种入口可以共享测试和数据语义。

代价：需要先抽取 application service 和显式存储生命周期；TUI 需要额外处理终端恢复、窄窗口和跨平台输入；入口和契约数量增加后需要持续维护兼容测试。

## 风险与控制

- TUI 复杂度膨胀：默认首页只保留资源浏览，高级模块通过命令面板和独立页面逐步披露。
- CLI/TUI 语义漂移：禁止 TUI 解析 CLI 文本，所有入口共用 service，并以黑盒测试锁定 JSON 和退出码。
- 单条取用体验变差：P0 同时交付 `ttl pick --print`。
- 远端或同步影响本地使用：本地优先，网络错误只能影响同步操作，不能阻塞本地浏览和编辑。

## 验证方式

该决策在 M1-M5 里程碑中验证：

- CLI/CI 在无 TTY 下通过 JSON、stdin/stdout 和退出码完成自动化。
- `ttl pick --print` 可以在一条命令中输出选中资源并干净退出。
- `ttl ui` 的资源增删改查、搜索和标签操作与 CLI 共享同一数据语义。
- macOS、Linux/SSH、Windows Terminal 的终端恢复和窄窗口验收通过。

若这些指标不能满足真实使用场景，再单独创建新的决策记录评估原生弹窗、Web UI 或其他交互形态。
