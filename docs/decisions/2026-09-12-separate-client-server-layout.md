# Separate Client And Server Layout

日期：2026-09-12
状态：adopted（源码边界已采用；云端独立交付由 W-010 跟踪）
任务：W-004、W-006、W-010

## 背景

当前仓库把本地 CLI、远端 HTTP 服务、云端客户端、多租户存储和共享模型放在根目录、`command/`、`api/` 与 `db/` 中。`main.go` 同时定义客户端和服务端运维命令，`db/` 同时包含 SQLite、bbolt、HTTP 客户端和租户能力。目录名称无法准确表达代码属于本地客户端、远端服务还是共享核心。

项目方向还计划增加 TUI。如果继续让 TUI 直接依赖 Cobra 全局状态和 `db.Stor`，客户端入口之间难以共享可测试的业务逻辑。

## 决定

将系统定义为两个独立应用工程。这里的应用工程是可独立构建、测试、发布、部署和回滚的单元，不要求对应独立 Git 仓库或 Go module：

- `cmd/ttl` 构建本地客户端应用，CLI 和 TUI 是同一客户端的两种交互入口。
- `cmd/ttl-server` 构建远端多租户云服务，拥有独立制品、部署配置和运行权限。
- `internal/client`、`internal/server`、`internal/core` 分别承载客户端用例、服务端用例和共享领域契约。

源码暂时保留在同一个仓库和 Go module 中。SQLite、bbolt 等具体存储实现放在 `internal/storage`。客户端与服务端不得直接互相 import，只通过共享 core 或 `/api/v1` 契约交互。项目处于开发阶段，直接删除根目录构建入口、`ttl server`、旧包门面和旧数据格式支持，迁移直接收敛到目标入口和包边界。

客户端存储生命周期由 `internal/client/cli` 的命令组装层拥有：它根据命令行和配置创建一个 `internal/client/app.Service`，通过命令 context 注入本次执行，命令和同步用例只依赖该显式服务；命令执行结束后由客户端入口关闭服务。旧 `db.Stor` 全局变量、`db` 存储操作门面和客户端 `ttl server` 兼容代理不再作为目标接口保留。

独立编译不等于独立部署。发布系统必须分别生成 `ttl` 和 `ttl-server` 制品；云端运行环境只获得 `ttl-server` 及明确声明的运行文件，不得依赖客户端二进制、客户端配置或源码目录。两个制品可以共享 Git tag 和流水线模板，但必须能够单独构建、发布、升级和回滚。

## 备选方案

- 使用顶层 `frontend/` 和 `backend/`：名称直观，但无法合理安置共享模型和存储接口，容易形成两个新的大杂物包。
- 拆为客户端与服务端两个仓库：源码隔离最强，但不是实现独立部署的必要条件；当前共享数据模型和存储语义较多，会立刻引入版本联动和发布维护。
- 保持当前包，只补充文档：改动最小，但不能解决 `main.go`、`db/` 和全局存储造成的实际依赖交叉。
- 立即拆为多个 Go module：能强化依赖边界，但当前阶段会增加 replace、版本和测试矩阵成本。

## 影响

收益是客户端、服务端和共享核心能从路径直接识别，CLI 与 TUI 可以复用业务用例，服务端拥有独立构建和部署生命周期。代价是迁移会影响大量 import、测试和构建脚本，并要求维护两个发布制品以及服务端部署流程。

删除旧入口或调整数据、配置与 `/api/v1` 契约时，同一变更必须同步更新所有调用方、测试和文档，不提供过渡代理、双写或旧格式读取。阶段 A 已建立 `cmd/ttl-server` 和 `internal/server/cli`，阶段 C 的客户端存储生命周期由 W-006 落实；旧入口清理以及独立云端发布、部署和回滚仍需完成后才能宣称拆分全部完成。

## 验证

按 `docs/client-server-separation-plan.md` 分阶段验证两个二进制构建、包依赖方向、CLI 黑盒回归、API/同步集成测试以及 `go vet`。架构检查必须禁止 `ttl` 依赖服务端包。独立交付还需验证发布系统分别生成两个制品，云端部署只包含 `ttl-server` 运行内容，并且服务端可以脱离客户端制品和源码目录独立启动、升级和回滚。

W-006 的实现验证还必须证明客户端命令不读取全局存储，服务在初始化失败时不会泄漏已打开的资源，正常退出和 workspace 切换都会关闭当前存储。
