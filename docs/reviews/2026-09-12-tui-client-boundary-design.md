# TUI、CLI 与客户端边界设计评审与整改复核

- 结论：`PASS`（仅基础 TUI / W-007 范围）

总体方向可以继续：CLI 和 TUI 是同一个 `ttl` 客户端的两种交互形式，共用业务服务、存储契约和远端 API；CI 只是 CLI 的运行环境；服务端不需要区分 CLI 与 TUI。

本轮复核基于后续形成的范围基线、需求展开和任务拆分。原评审中的大部分问题已经通过文档整改和范围拆分得到处理；项目负责人已确认基础 TUI 的阶段承诺，因此本评审对 W-007 放行。候选能力仍按独立需求和评审流程管理。

## 评审发现（历史记录及当前结论）

### MEDIUM-1：P0 同时扩展 TUI、CLI 和搜索契约，范围大于“实现 TUI”（已解决）

- 位置：`tui-master-plan.md` 第 4.3、5.8、10、12 节；`ttl-product-direction.md` 第 8.1 节；交互策略决策记录“提议方案”第 2、3 项。
- 问题：P0 除 `ttl ui` 外，还强制包含 value 全文搜索、`ttl search/list`、`--json`、`--non-interactive`、stdin/stdout、稳定退出码和 `ttl pick --print`。这些是有价值的客户端增强，但不是让 TUI 与现有 CLI 共用业务能力的必然条件。
- 后果：W-007 无法作为一个边界清晰的 TUI 任务拆分；任一 CLI 契约未完成都会阻塞 TUI 首版，变更和测试范围也会同时扩大。
- 原整改：由 W-007 的设计负责人把“最小 TUI 闭环”“通用客户端前置重构”“可选 CLI 增强”“快速选择模式”拆成独立交付物。
- 复核结果：已固化为 [`docs/task-breakdowns/2026-09-12-tui-scope-split.md`](../task-breakdowns/2026-09-12-tui-scope-split.md) 中的 T-01/T-02/T-03/T-04。基础 TUI 只引用阶段承诺；CLI 机器契约和 `ttl pick` 均为候选，不再阻塞 T-02。

### MEDIUM-2：能力地图混合已确认范围与产品候选，容易把路线图误读为承诺（已解决）

- 位置：`tui-master-plan.md` 第 5、11.2、12 节；`ttl-product-direction.md` 第 7.3、8、9、10、12 节。
- 问题：`kind`、`favorite`、`archived`、批量操作、保存搜索、搜索历史、草稿恢复、鼠标、本地 Web UI、插件等能力已被排进 P1-P3；产品方向还把复制、备份、工作日志等列入第一阶段或后续阶段。当前讨论只确认了单用户边界和 CLI/TUI 关系，没有逐项批准这些产品能力。
- 后果：候选功能会在拆任务时变成默认需求，掩盖首版真正需要验证的使用闭环。
- 原整改：由产品范围文档负责人逐项标注“已确认”“候选”“明确不做”；未确认能力保留在候选清单，不进入承诺里程碑和验收标准。
- 复核结果：[`ttl-product-direction.md`](../ttl-product-direction.md) 已建立四种能力状态，TUI 能力地图增加状态映射，候选集中到 [`ttl-future-roadmap.md`](../ttl-future-roadmap.md)。首期需求只使用现有核心字段，不因能力地图自动新增数据字段；能力地图中标签批量操作、工作区/批量删除确认也已明确为后续候选，不再混入 P0 资源闭环。

### MEDIUM-3：CRDT 和多设备演进容易被理解为多人协作路线（已解决）

- 位置：`tui-master-plan.md` 第 12 节 P3、第 13 节；`client-server-data-flow.md` 第 8 节；`ttl-product-direction.md` 第 6、11、15 节。
- 问题：产品边界明确不支持账户间分享、协作者、资源权限和多人实时编辑，但路线图仍把版本向量和 CRDT 放在演进链路中；当前实现文档又给出完整的多客户端改造建议。技术上，同一个 API Key 可以被两个进程或设备使用，CLI 与 TUI 也可能同时运行，但这只是同账户并发风险，不等于在线表格式协作。
- 后果：读者可能误以为 TUI 需要为多人协作预留协议，过早引入高复杂度同步设计。
- 原整改：当前 TUI 范围只记录“单账户、建议单主动写端”的约束和现有丢失更新风险；未来多设备先评审 revision/ETag、冲突提示和幂等，CRDT 不作为默认下一步。
- 复核结果：产品基线和任务拆分均将多设备保留为技术风险，明确排除多人协作；T-02 不含 CRDT、版本向量或多设备一致性依赖。

### MEDIUM-4：总体设计把目标 HTTP 契约写成了现有契约（非阻塞后续项）

- 位置：`tui-master-plan.md` 第 10.3 节；`client-server-data-flow.md` 第 7 节；`internal/server/api/types.go` 的 `CreateResourceRequest`；`internal/client/remote/storage.go` 的 `SaveResource`、`UpdateResource`。
- 问题：总体设计原先声称 `POST /api/v1/resources` 当前支持可选 `tags`，但服务端创建 DTO 只接收 `key` 和 `value`；客户端虽发送 `tags`，服务端会忽略。远端更新也只发送 `value`。
- 后果：按总体设计实现 TUI 会假定标签已可靠写入远端，实际可能静默丢失标签，CLI/TUI 数据语义也无法一致。
- 当前处理：总体设计和数据流文档已按当前读取、独立标签接口、创建、更新和同步行为区分现状与目标。代码仍存在远端客户端未完整接入标签增删路由、创建/更新 DTO 未完整处理 `tags` 的缺口。
- 放行判断：该差异不影响本地资源闭环，因此不阻塞 T-02；在远端 TUI 或同步增强进入范围前，必须单独补需求、技术方案、接口/集成测试和一致性验收。

### MEDIUM-5（已解决，放行前状态）：提案状态与 M0“已完成”相互矛盾

- 位置：`tui-master-plan.md` 文首和第 4.3 节；交互策略决策记录的 `proposed` 状态。
- 原问题：总体设计仍是提案，关联决策也未采纳，但 M0 曾声称总体设计已经完成并通过人工评审。
- 风险：后续可能在范围尚未确认时直接进入 WBS 或实现。
- 放行前修正结果：已将 M0 标为“待评审”；总体设计保持“提案”，交互策略保持 `proposed`，整体评审保持 `CONDITIONAL`，基线保持“基线草案，待评审确认”。
- 验证结果：`tui-master-plan.md`、交互策略决策记录、基线、评审结论和 `WORK_ITEMS.md` 的状态表述已一致；只有完成范围确认后，M0 才能改为“已完成”。

### LOW-1：`ttl pick` 的形态已澄清，但优先级尚未得到独立确认（已解决为候选）

- 位置：`tui-master-plan.md` 第 2、4.3、6、12 节；交互策略决策记录“决策”第 2 项。
- 问题：`ttl pick` 已正确归类为短生命周期 TUI 模式，不是 CLI、TUI 之外的第三种客户端；但文档仍把它作为 P0 必交付内容。
- 后果：快速取用体验的实验会与完整 TUI 首版绑定，扩大首版交付面。
- 复核结果：`ttl pick` 已由 T-04 独立跟踪为候选能力，首期优先级和 `--print` 仍需单独确认；延期不会阻塞 `ttl ui`。

### LOW-2：当前实现图只标 CLI，未表达计划中的同一客户端边界（已解决）

- 位置：`client-server-data-flow.md` 第 2 节。
- 问题：正文说明客户端包含现有 CLI 和计划中的 TUI，但结构图只写 `ttl CLI`。
- 后果：读者容易把 TUI 误解成另一套存储或另一种服务端客户端。
- 复核结果：数据流图、术语说明和交互策略决策记录均统一使用 `ttl client`，并区分 CLI 已实现、TUI 计划中。

## 当前一致的设计基线（待正式确认）

以下内容在几份文档之间一致，可以作为后续调整的稳定起点：

1. `ttl` 是客户端，`ttl-server` 是可独立构建和部署的后端。
2. CLI 和 TUI 是同一个客户端的两种交互形式，能力应落在同一 application/core/storage 契约上；它们不是两个租户，也不各自拥有一份业务规则。
3. CI 只是 CLI 的无 TTY 运行环境，不是“CI 客户端”；文件名和正文不再使用“CLI/TUI/CI 三客户端”的表述。
4. 服务端只按 API Key 识别账户/租户，不需要知道请求来自 CLI 还是 TUI。
5. 当前资源归单一账户所有，不支持跨账户分享、协作者、资源级权限或多人实时编辑。
6. 同一账户在两个进程或设备中使用在技术上可能发生，因此要记录数据覆盖风险；这不构成多人协作功能承诺。
7. TUI 尚未实现；`client-server-data-flow.md` 记录当前实现，其余三份文档主要描述提案或目标。

| 文档 | 应负责的内容 | 不应负责的内容 |

| TUI/CLI 交互策略决策记录 | 为什么保留 CLI、如何让 CLI/TUI 共用核心、为何暂缓其他入口 | 任务状态、完整功能清单、当前实现流水账 |
| `client-server-data-flow.md` | 代码当前如何存储、连接、同步、失败以及已知缺口 | 未来架构承诺和未经批准的协议方案 |

## 建议的最小首版范围

以下是评审建议，不是已经批准的需求：

1. 前置条件：完成显式存储生命周期和可复用的资源 application service，CLI 行为保持不变。
2. `ttl ui` 首版只完成本地资源的列表/搜索、查看、创建、修改、标签和删除确认，以及空态、错误态和终端恢复。
3. 首版复用现有资源字段，不新增 `kind`、`favorite`、`archived`。
4. 远端连接和同步页可以复用现有能力，但在标签契约和冲突语义修复前不承诺“与本地完全一致”。
5. `ttl pick`、新的 CLI JSON/非交互契约、批量操作、Web UI、后台同步和 CRDT 分别立项，不默认阻塞基础 `ttl ui`。

## 当前放行条件

本轮整改已足以支持 W-007 的技术方案和实现；总体长期设计及候选能力仍不自动冻结或放行。当前边界如下：

1. [`ttl-product-direction.md`](../ttl-product-direction.md) v0.2 的阶段承诺、候选能力和明确不做项已由项目负责人确认，基线状态已更新为“已确认”。
2. 基础 TUI 只能按 T-01/T-02 的边界推进：本地资源列表/搜索、查看、创建/修改、标签维护、安全删除及对应异常状态；候选任务延期不得阻塞它。
3. T-03 CLI 可组合性和 T-04 `ttl pick` 在实现前分别完成独立需求、技术方案和方案评审，并先更新基线状态；不得从 TUI 需求自动获得交付资格。
4. 远端标签契约差异暂不阻塞本地 TUI；只有远端 TUI、同步或标签一致性增强进入范围时，才需要单独完成接口修复、集成测试和冲突语义验收。

本评审的 `PASS` 仅适用于基础 `ttl ui` / W-007。总体设计仍是长期提案；`ttl pick`、CLI 机器契约之外的新增能力、P1/P2/P3 路线仍需各自完成范围确认、技术方案和评审。
