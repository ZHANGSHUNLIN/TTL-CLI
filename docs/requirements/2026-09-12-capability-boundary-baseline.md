# TTL 能力边界基线落地与首期需求展开

日期：2026-09-12
任务：W-011
状态：reviewed（基础 TUI / W-007 范围已确认）
基线：[`docs/ttl-product-direction.md`](../ttl-product-direction.md) v0.4

## Problem And Goal

当前工程已经积累了产品方向、TUI 路线、客户端与服务端边界以及数据流说明，但这些材料的状态和职责并不完全一致。候选能力可能被误读为已承诺范围，需求也可能在设计或实现过程中顺手扩大。

本需求用于把 [`docs/ttl-product-direction.md`](../ttl-product-direction.md) 落地为全工程的范围基线，并基于该基线展开首期本地资源管理需求。完成后，任何新增需求都能判断是否属于当前工程、当前阶段承诺、长期候选或明确不做，并能在进入技术设计前发现范围偏移。

## Scope

### In Scope

- 将产品定位、客户端/服务端工程边界、数据和开发阶段变更边界集中在一份基线文档中。
- 为能力建立 `现有能力`、`阶段承诺`、`候选能力`、`明确不做` 四种状态。
- 固化当前阶段的最小本地资源管理闭环：添加、搜索、查看、编辑、标签维护和安全删除。
- 保留现有 CLI 核心语义，并约束 CLI 与 TUI 共享同一份数据和业务规则。
- 明确需求从候选或明确不做范围进入阶段承诺时的评审、记录和任务门禁。
- 为后续各项需求提供可引用的范围、异常、变更影响和验收基线。

### Out Of Scope

- 实现 TUI、CLI 新命令、服务端 API、同步协议或存储迁移。
- 在本需求中决定 Go 包、接口、数据库表、依赖或代码结构。
- 将基线之外的候选能力自动转为首期承诺；候选能力另见 [`TTL 后续能力规划`](../ttl-future-roadmap.md)。W-013 的独立范围变更记录在其需求、方案和评审中。
- 引入多人协作、跨账户分享、资源级权限、原生桌面端、移动端、SaaS、AI、自然语言操作或 MCP。
- 用本需求替代具体功能的独立需求、技术设计和测试方案。

## Use Cases

1. **新需求归类**：提出一个新功能时，需求负责人能在基线中找到对应能力状态；如果它是候选或明确不做，需求不会直接进入技术设计。
2. **首期闭环展开**：产品负责人能从基线确定首期只围绕本地资源完成添加、搜索、查看、编辑、标签和安全删除。
3. **契约变更检查**：涉及 CLI、数据文件、配置、存储契约或 `/api/v1` 的需求，必须同步更新全部调用方、测试和文档，不保留旧行为。
4. **实现中发现扩张**：开发过程中出现顺手增加字段、入口、批量行为或同步能力时，能够退回需求阶段，而不是并入当前任务。
5. **评审范围判断**：评审者可以根据基线、需求的 In Scope/Out Of Scope 和验收标准判断实现是否越界。

## Rules

- 基线是产品范围的唯一入口；路线图、讨论记录和代码草稿不能单独产生产品承诺。
- 当前实现以代码、测试和 `docs/client-server-data-flow.md` 为准；当前实现存在不等于本阶段必须继续扩展。
- `阶段承诺` 才能进入当前阶段的具体需求；`候选能力` 和 `明确不做` 必须先完成范围变更。
- 首期资源模型只使用 `key`、`value`、`tags`、`created_at` 和 `updated_at`，不得由 TUI 或单个功能隐式增加字段。
- CLI 和 TUI 是同一客户端的交互形式，必须共享数据和业务规则；服务端不根据入口分别定义业务语义。
- 本地查看和编辑不依赖网络或同步服务可用；同步属于后置能力，不能阻塞本地闭环。
- 删除、覆盖、push、pull 和批量操作不能默认造成不可解释的数据损失。
- 每份后续需求都必须填写 In Scope、Out Of Scope、异常场景和可观察验收标准，并链接本基线。
- 基线范围变化必须先更新基线版本和变更记录，再更新需求、路线图和 `WORK_ITEMS.md`。

## Edge And Failure Cases

- **新能力无法分类**：标记为开放问题或候选能力，不得直接进入技术设计。
- **需求同时包含承诺和候选内容**：拆成独立需求或独立范围项，候选部分不能阻塞首期闭环。
- **需求与明确不做冲突**：保留冲突记录，等待基线重新评审；不能用技术方案绕过范围限制。
- **当前代码缺少基线承诺能力**：记录为实现缺口，不把“当前不存在”改写成“产品不需要”。
- **实现过程中发现新增字段、入口或接口**：暂停该扩展，补充范围和调用方影响评估，必要时新建工作项。
- **文档之间状态不一致**：以基线为范围判断依据，以代码和数据流文档为当前行为依据，并在评审中记录差异。
- **基线评审未通过**：文档可以作为草案供需求分析使用，但不能把未决能力标为已承诺，也不能据此放行实现。

## Acceptance Criteria

- [ ] `docs/ttl-product-direction.md` 已标明基线版本、状态、适用范围和生效条件。
- [ ] 基线文档明确列出客户端、服务端、数据、开发阶段变更和本地优先边界。
- [ ] 基线文档把能力区分为 `现有能力`、`阶段承诺`、`候选能力` 和 `明确不做`，并说明各状态的使用规则。
- [ ] 基线文档明确当前阶段的最小本地资源闭环，且没有把候选能力写成自动承诺。
- [ ] 基线文档包含范围变更门禁：需求归类、In Scope/Out Of Scope、影响评估、评审、基线更新和任务更新顺序。
- [ ] 本需求文档的 In Scope、Out Of Scope、规则、异常和验收标准均能回链到基线，且不包含技术实现设计。
- [ ] `WORK_ITEMS.md` 有对应工作项，链接本基线和本需求，并列出文档检查与评审证据。
- [ ] 评审文档中引用的产品方向章节与升级后的基线章节一致。
- [ ] `git diff --check` 通过，文档内部链接和关键术语人工核对通过。
