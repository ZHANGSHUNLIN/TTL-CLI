# 工作流看板模型升级需求

日期：2026-09-13
任务：W-014
状态：reviewed
基线：[`docs/personal-development-workflow.md`](../personal-development-workflow.md)

## 问题与目标

当前看板只记录 `Inbox`、`Doing`、`Review`、`Blocked`、`Done` 五个生命周期状态。任务正文也只有目标、验收、检查、决策和备注，导致页面无法表达任务是 feature、bug 修复、文档还是其他工作，也无法显示需求分析、技术设计、方案评审、WBS、编码、测试和提交进度。

目标是让看板同时回答两个问题：

1. 任务当前处于哪个生命周期状态，是否可以继续推进。
2. 任务属于什么类型，当前研发阶段是什么，阶段产物和阻塞点在哪里。

升级不能把所有任务强行套成 feature，也不能把八个研发阶段简单变成八个看板列。生命周期继续用于统一的流转控制；阶段进度和任务类型用于解释任务内容。

## 范围

### In Scope

- 任务类型：`feature`、`bugfix`、`refactor`、`docs`、`chore`、`spike`、`other`。
- 任务优先级：可选的 `P0`、`P1`、`P2`、`P3`。
- 当前研发阶段：从任务阶段清单中选出的一个阶段。
- 阶段清单：任务实际适用的阶段及其顺序；不同类型可以跳过不适用阶段。
- 阶段产物：需求、技术方案、方案评审、WBS、代码、测试、交付评审和提交等链接或证据。
- 父任务、依赖任务、阻塞原因和下一步动作的可见展示。
- 看板卡片、任务详情和项目文档入口对上述信息的展示。
- 旧 `WORK_ITEMS.md` 和 `WORK_ITEMS.json` 的兼容读取；缺少新字段的任务显示为“未分类/未设置”，不能导致项目加载失败。
- 更新项目流程文档、任务模板、文档索引和字段说明。

### Out Of Scope

- 自动推断任务类型、阶段或完成度。
- 自动修改任务 Markdown、自动生成需求/方案/代码或自动创建 commit。
- 用新阶段替换现有五个生命周期状态。
- 多人协作、远程审批、权限、通知、工时、甘特图和跨项目依赖计算。
- 修改项目业务代码、CLI 行为或产品数据。

## 任务类型与阶段规则

任务类型决定推荐模板，但不自动替任务做范围判断：

| 类型 | 典型目标 | 默认要求 |
| --- | --- | --- |
| `feature` | 新增用户能力或完整流程 | 需求、方案、方案评审、WBS、实现、测试、交付评审、提交 |
| `bugfix` | 修复已有行为缺陷 | 问题与影响、修复、回归测试、交付评审、提交；跨包或高风险修复可增加方案评审 |
| `refactor` | 不改变目标行为的结构调整 | 影响范围、方案、实现、测试、交付评审、提交 |
| `docs` | 文档、规范或流程更新 | 目标、内容变更、文档检查、交付评审、提交 |
| `chore` | 构建、依赖、脚本或维护工作 | 变更说明、验证、交付评审、提交 |
| `spike` | 有明确问题边界的调查或验证 | 问题、调查、结论或决策；不要求伪造实现阶段 |
| `other` | 无法归入以上类型的工作 | 必须在备注中说明采用的阶段清单和验收方式 |

任务可以覆盖默认要求，但必须在阶段清单或备注中说明跳过原因。看板不根据类型自动移动状态。

## 生命周期与阶段的关系

- `Inbox`：任务已登记，尚未开始；不应有“当前进行中的阶段”。
- `Doing`：任务正在需求分析、方案、评审、拆分、实现、测试或验证中的任一阶段。
- `Review`：实现或交付内容已完成，等待人工审核；阶段应为 `delivery_review` 或类型对应的最终审核阶段。
- `Blocked`：由于明确的外部依赖、待决策或技术阻塞无法继续；必须有阻塞原因和下一步。
- `Done`：验收、检查、人工审核和本地提交均完成。

阶段是任务内部进度，不替代生命周期状态。阶段未完成的任务不能仅因为文档齐全而进入 `Review`。

## 任务信息契约

任务正文在 `WORK_ITEMS.md` 中增加以下可选字段；状态仍由 `WORK_ITEMS.json` 维护：

```md
- W-XXX 任务标题
  - 类型：feature
  - 优先级：P1
  - 当前阶段：requirements
  - 阶段清单：requirements,design,design_review,breakdown,implementation,tests,delivery_review,commit
  - 父任务：W-XXX（没有则写“无”）
  - 依赖：W-XXX, W-YYY（没有则写“无”）
  - 产物：需求=docs/requirements/...；方案=docs/tech-designs/...；评审=docs/reviews/...
```

字段缺失时使用兼容默认值，不从标题或文件路径猜测。阶段名称使用稳定英文 ID，页面显示本地化名称。

## 页面验收目标

- 卡片能看到任务类型、优先级、生命周期状态和当前阶段。
- 卡片能看到阶段进度，例如 `需求分析 1/8`，但不会把跳过的阶段误算为未完成。
- 详情页显示阶段时间线、适用阶段、产物链接、父任务、依赖、阻塞原因和下一步。
- 详情页仍保留目标、验收、检查、决策、备注和评审记录。
- 缺失元数据的旧任务显示明确的“未分类/未设置”，并可正常打开。
- 项目文档浏览器仍能打开阶段产物；不存在的链接必须显示为普通文本或不可用状态，不能导致看板失败。

## 异常与边界场景

- 未知任务类型、优先级或阶段：项目加载成功，字段显示为“未知”，并在详情中提示修正。
- 阶段清单为空但当前阶段非空：显示当前阶段，不计算进度，并提示阶段清单缺失。
- 当前阶段不在阶段清单中：显示不一致警告，不擅自插入或删除阶段。
- 阶段清单包含重复项：保留原始顺序，进度计算按首次出现处理，并提示重复。
- 依赖任务 ID 不存在：显示为未解析依赖，不阻塞其他任务加载。
- 产物路径位于项目外部：只显示路径文本，不允许文档 API 读取项目外文件。
- 旧 metadata 没有新字段：按兼容默认值显示，不要求迁移才能打开项目。
- Markdown 字段格式错误：忽略无法解析的字段并保留任务正文，不因单项格式错误使整个看板不可用。

## 验收标准

- [ ] 新旧 `WORK_ITEMS.md`/`WORK_ITEMS.json` 均可加载，旧任务不会因缺少新字段失败。
- [ ] 任务类型、优先级、当前阶段、阶段清单、父任务、依赖和产物可被解析并通过 board API 返回。
- [ ] 未知值、缺失值、重复阶段和阶段不一致均有可观察提示，且不会破坏整板加载。
- [ ] 看板卡片显示类型、优先级和阶段进度；详情页显示阶段时间线和产物/依赖信息。
- [ ] 不同阶段清单的任务能正确计算进度，跳过阶段不被计为未完成。
- [ ] 五个生命周期状态的移动、Review 打回和 Done 归档行为保持兼容。
- [ ] 评审评论、项目文档浏览和归档页面不回归。
- [ ] 文档模板、工程流程说明、W-014 任务卡与实际字段保持一致。
- [ ] dashboard 单元测试、HTTP 测试和浏览器冒烟覆盖上述正常、兼容和异常路径。

## 开放问题与假设

- 本需求假设阶段元数据由任务拥有者在 Markdown 中维护；看板只解析和展示，不自动补全。
- 是否在后续增加页面内编辑类型、阶段和产物，不属于本次升级；当前仍通过项目文件修改。
- 阶段清单的 ID 集合由流程文档维护；本次先提供稳定的通用阶段 ID，不为每种类型强制生成模板文件。
