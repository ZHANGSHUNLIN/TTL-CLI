# W-010 需求分析：云端服务独立交付

日期：2026-09-13
任务：W-010
状态：需求已确认，方案评审通过（PASS）

## 问题与目标

仓库已经有独立的客户端和服务端入口，但 CI 和发布流程仍执行已删除的
`go build .`，并且只发布一个客户端名称的制品。`ttl-server` 目前也只启动
明文 HTTP 监听，没有健康检查、信号驱动的优雅关闭或升级回滚流程。服务端
因此无法脱离源码目录和 `ttl` 客户端完成可重复的获取、安装、升级和回滚。

本任务的目标是让 `ttl-server` 成为独立交付的应用：能够单独构建、识别、
安装、观测、重启和恢复，服务端机器不需要安装 `ttl` 客户端，也不需要复制
仓库源码。

## 当前事实

- 支持的可执行入口是 `./cmd/ttl` 和 `./cmd/ttl-server`。
- 现有 CI 和 release workflow 仍执行 `go build .`，没有反映当前入口布局。
- 服务端当前接受 `--port` 和 `--data-dir`，读取 `<data-dir>/users.json`，
  在 `<data-dir>/tenants/` 下创建每个用户的 bbolt 数据，并以 `:<port>`
  监听明文 HTTP。
- 服务端没有健康检查端点、优雅关闭、TLS 边界或升级/回滚流程文档。
- API Key 保存在 `users.json`；当前文件写入权限为 `0600`，父目录由现有实现
  创建。
- 仓库仍保留一个 Git 仓库和一个 Go module，本任务不拆分它们。
- W-017 是前置的结构收敛任务。W-010 只能在 W-017 确认服务端最终代码归属
  后增加生命周期实现，不能再建立第二个长期服务端入口。

## 交付基线

第一版独立交付采用明确且克制的范围：

- 客户端继续支持现有 Linux、macOS 和 Windows 构建矩阵。
- 服务端只承诺 Linux `amd64` 和 `arm64`，发布压缩 tarball 及 SHA-256 校验文件。
  不承诺 Windows 或 macOS 服务端制品。
- 服务端 tarball 只包含 `ttl-server` 和用于识别版本的发布元数据，不包含
  `ttl`、客户端配置、工作区数据、用户数据或源码。
- 参考部署使用带版本号的 release 目录和稳定的 `current` 符号链接，由 systemd
  或语义等价的进程管理器托管。
- TLS 由受管反向代理或负载均衡器终止。服务端只在回环或私有网络监听明文
  HTTP，不允许直接暴露到公网。
- 容器镜像、Kubernetes/Helm、自动证书签发、高可用和数据库 schema 迁移不在
  W-010 范围内，可另立任务。

## 范围

### 构建与发布

1. CI 从 `./cmd/ttl` 构建客户端，从 `./cmd/ttl-server` 构建服务端，不再构建已
   删除的根入口。
2. tag 发布同时生成可分别下载的客户端和服务端制品；一方失败不能被另一方
   的成功状态掩盖。
3. 制品名称包含应用、版本、系统和架构；每个归档都有对应 SHA-256 校验文件。
4. 服务端制品可以在没有仓库 checkout、客户端制品和客户端配置的目录中直接
   解压运行。

### 运行时契约

1. `ttl-server serve` 在保留现有 `--port`、`--data-dir` 的基础上增加显式监听
   地址。默认绑定必须避免意外公网暴露；需要外部流量时由部署明确配置私有
   网络和 TLS 边界。
2. 启动时校验数据目录并加载用户存储；必需状态不可读或不可写时，在监听前
   以非零状态退出。
3. `GET /healthz` 不需要认证。服务就绪后返回 HTTP 200 和简短 JSON；尚未就绪
   时返回非 200；响应不得泄露用户、API Key 或资源内容。
4. SIGTERM 和 SIGINT 触发优雅关闭：停止接受新连接，在限定时间内等待进行中
   请求，关闭全部租户存储；超时必须结束进程，不能无限等待。
5. 运维日志写入 stdout/stderr 交给进程管理器收集，默认不记录 API Key 和资源值。
6. 服务端启动和请求处理不得读取客户端配置、客户端工作区或客户端二进制。

### 部署、升级与回滚

1. 参考部署必须说明专用非 root 用户、执行目录、数据目录、日志收集、健康探针
   以及防火墙/TLS 边界。
2. 数据目录继续使用 `users.json` 和 `tenants/<user-id>/data.db`，不在本任务中
   静默转换数据或双写两种格式。
3. 升级先校验制品，在新的不可变 release 目录中完整安装，再切换 `current`，
   重启服务并检查 `/healthz`。
4. 启动或健康检查失败时，可以停止失败版本、恢复旧的 `current` 指针并重启，
   且不修改旧 release 目录。
5. 升级前创建数据备份或文件系统快照。跨未来不兼容数据迁移的回滚不属于本
   任务，迁移必须单独设计恢复方案。

## 非目标

- 改变客户端 CLI/TUI、同步语义或 `/api/v1` 资源协议。
- 拆分 Git 仓库或 Go module。
- 云账号、DNS、负载均衡、证书签发和防火墙资源的实际配置。
- OCI 镜像、Kubernetes、Helm、自动扩缩容和高可用。
- 新认证方案、API Key 哈希、多地域复制或资源级授权。
- 自动数据库迁移，或承诺任意历史版本都能读取未来数据格式。

## 使用流程

### 获取并安装发布制品

1. 创建或接收版本 tag。
2. CI 独立构建并上传客户端和服务端制品。
3. 运维下载 Linux 服务端归档和校验文件，校验成功后只将服务端文件解压到
   带版本号的目录。
4. 进程管理器指向服务端可执行文件，并挂载独立的数据目录。

### 启动与探活

1. 以显式的 `--data-dir`、`--listen` 和 `--port` 启动 `ttl-server serve`。
2. 服务端加载 `users.json`、初始化租户管理器后才报告就绪。
3. 进程管理器探测 `/healthz`；业务请求继续使用现有 `/api/v1` 认证和租户语义。

### 升级与恢复

1. 升级前创建数据快照并校验新归档。
2. 新版本解压到旁边的 release 目录，切换稳定指针并重启。
3. 在限定时间内检查 `/healthz` 和一次认证 API 请求。
4. 失败时恢复旧指针并重启；失败版本保留用于诊断，不作为活动版本。

## 规则与兼容性

- 现有 `ttl-server user add/list/enable/disable/reset-key/delete` 继续使用同一
  `--data-dir`。
- 现有客户端继续使用 `/api/v1` 和 `Authorization: Bearer <api-key>`；不改变
  资源 payload 或租户隔离。
- 服务端独立可运行必须具备自己的二进制、运行目录、配置参数、数据目录和进程
  管理流程。
- 归档可以包含版本识别信息，但不能嵌入用户数据和密钥，也不能在日志中打印。
- 默认监听和文件权限遵循最小暴露原则；公开访问必须经过文档化的私有网络或
  TLS 代理边界。

## 边界与失败场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| 根入口不存在 | 客户端和服务端从明确的 `cmd/` 路径仍能构建 |
| 制品缺失或校验失败 | 安装/升级停止，不改变活动 release |
| `users.json` 损坏或不可读 | 启动以非零状态退出，不开始监听 |
| 数据目录不可创建或写入 | 启动失败并给出可操作错误 |
| 端口被占用 | 启动失败，不删除或改变已有数据 |
| 就绪前探活 | 返回非就绪状态，不暴露用户数据 |
| API 请求期间收到 SIGTERM | 请求受关闭超时约束，租户存储最终关闭 |
| 新版本健康检查失败 | 可以恢复旧 release 并重新启动 |
| 没有客户端二进制或配置 | `ttl-server` 仍能独立启动并提供 API |
| 公网 TLS 代理不可用 | 部署报告不健康；服务端不伪装成公网 TLS 终点 |

## 验收标准

- [ ] CI 从支持的 `cmd/` 入口构建 `ttl` 和 `ttl-server`。
- [ ] tag 发布生成独立命名的 Linux 服务端 `amd64`/`arm64` 归档和校验文件，且
      不包含客户端、源码或数据文件。
- [ ] 干净目录冒烟测试在没有 checkout 的情况下启动服务端并完成认证 API 请求。
- [ ] `--listen`、`--port`、`--data-dir` 的行为有文档和测试，默认监听不会意外
      暴露公网。
- [ ] `/healthz` 按约定返回就绪结果，不需要认证且不包含敏感信息。
- [ ] SIGTERM/SIGINT 在限定时间内完成请求排空和资源关闭。
- [ ] 参考部署说明最小权限、数据持久化、日志、健康探针和外部 TLS 终止。
- [ ] 临时部署目录可以重复演练升级和失败回滚，并包含升级前备份步骤。
- [ ] 既有 API、用户管理、租户隔离和客户端行为保持兼容。

## 未决问题与假设

- 本设计暂以 Linux systemd（或等价进程管理器）为首个参考部署；容器交付后置。
- 生产反向代理、DNS、证书和密钥备份由环境方负责，W-010 只约定边界和探针契约。
- 发布命名和版本注入方式在技术方案中固定后才能修改 CI。
- 如果必须由 `ttl-server` 直接提供 TLS，需要新增需求，重新设计证书和密钥生命周期。
- 生命周期组合根目录暂提议为 `internal/server/app`，必须与 W-017 最终结构一致，
  不得新增第二个服务端入口。
